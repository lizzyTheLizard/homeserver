# Design

## Context

`services/wichteln` is a small Next.js app with Server Actions (`app/actions.ts`, `app/admin/actions.ts`), a data layer in `lib/store.ts` that works on a `Queryable` (pg pool, transaction client or PGlite in tests), and an HMAC-signed session cookie (`lib/session.ts`) holding either `{ role: 'admin' }` or `{ role: 'user', groupId, userId }`. Schema: `wichteln_groups (id, name, phase, created_at)` and `wichteln_users (id, group_id, name, password, wish_*, selected_wish_of)`, with a unique index on `(group_id, lower(name))`. Today `password` is plain text, generated by `generatePassword()`, and shown on the admin group page. Participants sign in on `/`, where `authenticateParticipant` searches all groups by name and password and takes the first match. Write paths lock the group row (`lockGroup`, `SELECT … FOR UPDATE`) inside `withTransaction`.

See proposal.md for motivation and specs/wichteln/spec.md for the behavior.

## Goals / Non-Goals

**Goals:**
- One invite link per group, used both for registering and for signing in.
- Sign-in scoped to the group in the URL. No search across groups.
- Hashed passwords without adding a dependency.
- Keep the existing wish, selection and matching code untouched.

**Non-Goals:**
- Organizer or multi-admin accounts. The single env-configured admin stays.
- Rotating or disabling an invite link (deleting the group is the only way).
- Self-service "forgot password", or participants changing their own password.
- Rate limiting sign-in attempts.
- Invalidating a participant's existing session on password reset. The cookie holds only `userId`, and a reset is meant for someone who is locked out.
- Keeping existing groups. The user decided to drop them.

## Decisions

### Invite token separate from the group id
Add `invite_token TEXT NOT NULL UNIQUE` to `wichteln_groups`, filled at creation with `randomBytes(24).toString('base64url')` (32 characters). The link is `/g/<token>`, built from the request origin on the admin page (the copy button uses `window.location.origin` as `CopyCredentials` does today).
*Alternative:* use the group UUID in the link. It is random enough, but it also appears in admin URLs, and a separate token leaves room for rotating links later without a schema change. The extra column costs almost nothing.

### Route layout
- `/` — administrator sign-in only. A participant session still redirects to `/wunsch`. The page text tells participants to use their invite link. If the submitted name and password are not the admin's, the error says so and points to the invite link.
- `/g/[token]` — server page: `getGroupByInviteToken`, `notFound()` if missing. A participant already signed in to *this* group is redirected to `/wunsch`. Otherwise it renders the group name plus two client forms, `GroupLoginForm` and `RegisterForm`. The register form is replaced by a notice while `phase !== 'wishes'`. A visitor signed in to a different group sees the page normally, and signing in replaces the session.
- `/wunsch` — unchanged, except that logout redirects to the participant's invite page so they can sign in again easily. `logout` reads the session, looks up the group's token and redirects there, falling back to `/`.

### Group-scoped authentication
Replace `authenticateParticipant(db, name, password)` with `authenticateParticipant(db, groupId, name, password)`: select the user by `group_id = $1 AND lower(name) = lower($2)`, then `verifyPassword`. When no user matches, still run a dummy `verifyPassword` against a fixed hash, so timing does not reveal whether a name exists. The form posts the token as a hidden field. The action resolves token → group server-side and never trusts a posted group id.

### Password hashing with `crypto.scrypt`
New `lib/password.ts` with `hashPassword(plain): Promise<string>` and `verifyPassword(plain, stored): Promise<boolean>`. Format `scrypt$<N>$<r>$<p>$<salt b64url>$<hash b64url>`, with N=16384, r=8, p=1, a 16-byte random salt and a 32-byte key. Verification parses the parameters from the stored string, so they can change later, and compares with `timingSafeEqual`.
*Alternatives:* bcrypt/argon2 packages add a native or WASM dependency for a tiny app. Node's scrypt is built in and good enough.

### Registration
`registerParticipant(db, groupId, name, password)` in the store, called inside `withTransaction`. It locks the group, refuses if `phase !== 'wishes'`, checks for a case-insensitive duplicate in the group (friendly message), and inserts with `hashPassword`. As a backstop, a unique violation (`23505`) from the existing `(group_id, lower(name))` index maps to the same "Name ist bereits vergeben" error. The action validates first: name trimmed, 1–60 characters, password 8–200 characters, confirmation equal. After success it calls `setSession({ role: 'user', groupId, userId })` and redirects to `/wunsch`. Hashing runs before the transaction, so the group lock is not held during the ~50 ms scrypt call.

### Password reset
`resetPassword(db, groupId, userId): Promise<StoreResult<string>>` generates a password with the existing `generatePassword()` (10 characters, unambiguous alphabet), stores its hash and returns the plain value. The admin action `resetPassword(groupId, userId, prev, formData)` uses `useActionState`, so the new password lives only in that action's returned state and is rendered next to the participant once. A reload clears it. Allowed in every phase, since people may forget their password during selection.

### Store/API shape changes
- `createGroup(db, name)` — no participant list. Returns the group including `inviteToken`.
- Remove `addParticipants` and its admin action/form, and remove `CopyCredentials` (replaced by a `CopyInviteLink` client component).
- `User.password` goes away from the domain type. The hash is read only inside `authenticateParticipant`, so `getGroup`/`listGroups` never load it.
- `Group` gains `inviteToken`.
- `removeParticipant`, `deleteGroup`, `startSelection`, `saveWish`, `selectWish` and `matching.ts` stay as they are.

### Migration `db/002_invite_registration.sql`
```sql
DELETE FROM wichteln_groups;                       -- cascades to wichteln_users
ALTER TABLE wichteln_groups ADD COLUMN invite_token TEXT NOT NULL;
CREATE UNIQUE INDEX wichteln_groups_invite_token_idx ON wichteln_groups (invite_token);
ALTER TABLE wichteln_users RENAME COLUMN password TO password_hash;
```
`NOT NULL` without a default works because the table is empty after the `DELETE`. `001_init.sql` stays untouched, because the migrator checks hashes of applied migrations.

## Risks / Trade-offs

- [All existing Wichteln data is deleted on deploy] → This is what the user asked for. The prod DB is backed up nightly (see `infrastructure/README.md`) if something needs recovering.
- [Anyone holding the invite link can register during the wish phase] → The admin sees every participant and can remove strangers before starting selection. Registration closes when selection starts.
- [Online password guessing against a known name] → Minimum length of 8, scrypt cost per attempt, and a small closed audience. Rate limiting stays out of scope.
- [A participant loses the invite link] → The admin can copy the link again at any time from the group page. Participant sessions last 60 days.
- [A reset password is visible on the admin's screen] → Shown only in the action response, never persisted in plain text, and gone on reload.
