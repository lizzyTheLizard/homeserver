# Design

## Context

Both application Dockerfiles use the Next.js `output: 'standalone'` layout in a pnpm workspace: standalone output nests the app under `services/<name>/`, so the runtime working directory is `/app/services/<name>` and `static/`, `public/` and `db/` are copied in beside `server.js`. Differences that stay: `public/` and four revision `ARG`/`ENV`s (web only, switched by `revision-build-args` in `ci.yml` and set by hand in `pull-request.yml`), and the service name. `.dockerignore` already sits at the repository root and the build context is already `.`.

The backup lives in `infrastructure/db-backup/` and is built on the server by compose (`build: ./db-backup`); the deploy rsyncs `infrastructure/` and recreates the stack. It is `node:alpine` + `postgresql16-client` + five scripts (three Node.js `.mjs` with no npm dependencies, two shell) copied to `/usr/local/bin`, and has no tests, type checking or build. Change detection (`detect-changes.mjs`) knows `web`, `wichteln` and `dev-machine` services plus `infrastructure`. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Web and Wichteln Dockerfiles that are simple (one build stage plus one runtime stage) and identical except for the service name and the web-only `public/` and revision lines, kept alike by convention.
- The backup is a first-class workspace package: type-checked and linted with the shared configuration, built and published by the same pipelines, and started with the other services by `pnpm dev`.

**Non-Goals:**
- No build tool other than Dockerfiles (Buildpacks, `pnpm deploy`, `dockerfile_inline` in compose).
- No shared Dockerfile: each service keeps its own, as the backup must (its runtime differs in every part that is not the base image: `pg_dump`, no Next.js output).
- `services/dev-machine` is not touched.
- No change to the nightly dump, its schedule, the retention or the upload; the restore tool, the token helper and the run-now command are dropped on purpose (see below), and the optional variables keep their defaults, except `RETENTION_DAYS`, which is required outside development (the compose file sets 31).

## Decisions

**One Dockerfile per service, written alike.** `services/web/Dockerfile` and `services/wichteln/Dockerfile` stay where they are and keep being built with the repository root as context (`file: services/<name>/Dockerfile`), so the pipelines, change detection (`services/<name>/**`) and Renovate need no new concept. They contain the same text except for the service name in `@homeserver/<name>` and `services/<name>` and the web application's `public/` copy and revision `ARG`/`ENV` lines. Alternative: one root `Dockerfile` with `ARG SERVICE`; rejected because the backup needs its own file anyway and a per-service file keeps each image's definition next to its service.

**Official pnpm image, manifests first.** The build stage starts from `ghcr.io/pnpm/pnpm:<exact version>-alpine` (pnpm's documented Docker base; pnpm 12 is a native binary; its working directory is already `/app`), replacing `npm install -g pnpm@12`: Renovate tracks the pnpm version as an image tag. The image ships no Node.js, so the stage installs the version of `.nvmrc` with `pnpm runtime set node` (the pipeline's setup action reads the same file). Layers: copy the root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and the service's own `package.json`, `pnpm install --frozen-lockfile --filter @homeserver/<name>...`, copy the service's folder (not the other services, so a change elsewhere does not invalidate this build), build. The install layer is rebuilt only when dependencies change. A workspace project whose folder is absent from the build stage is not installed, as before. The runtime stage stays `node:<exact version>-alpine<x>` because pnpm is not needed there. Both stages use Alpine, because the standalone output contains native binaries (for example `sharp`) that must match the runtime's libc. `libc6-compat` is not installed. Alternatives: `pnpm fetch` + `pnpm install --offline` (pnpm's documented pattern for CI; rejected: it adds a step and downloads the dependencies of every service in the lockfile, while manifest-first gives the same layer caching); `npm install -g pnpm` in a Node image (the previous approach, floating pnpm version, extra step); the install script (`get.pnpm.io`), which pnpm documents for machines and CI runners rather than images and is not tracked by Renovate; Debian variants for both stages (safe fallback if `pnpm runtime set node` fails on musl, at the cost of larger runtime images).

**Revision args and `public/` stay web-only.** Wichteln does not read the revision and has no `public/` folder, so neither is added to its Dockerfile (no empty `public/` placeholder, no extra build args in its pipelines); the `revision-build-args` matrix switch in `ci.yml` stays for the web application only. The web application's revision lines sit in the runtime stage after all expensive layers so changing them never invalidates the build cache.

**Runtime stage uses the image defaults.** `node:<version>-alpine` runs as root by default and has a built-in `node` user (uid 1000), so the stage uses `USER node` and `--chown=node:node` instead of creating a user. The standalone server already defaults to port 3000 and sets `NODE_ENV=production` itself, so neither is set and `EXPOSE` (documentation only) is dropped. `HOSTNAME=0.0.0.0` is not set in the images but in the `environment` of the web and Wichteln services in `docker-compose.yml` (next to the `NODE_ENV` and `PORT` entries compose already has), because Docker sets `HOSTNAME` to the container id, which would make the server unreachable for the `localhost` health checks; a container run outside the compose file has to set it itself. The image's working directory is `/`, so the standalone output is copied to explicit `/app/...` paths and `WORKDIR /app/services/<name>` is set last. The `# syntax=` line is dropped because no instruction needs a newer frontend than the builder's.

**Backup as `services/backup`, a small TypeScript package like web and Wichteln.** The folder moves to `services/backup` and becomes the pnpm workspace package `@homeserver/backup` with the same scripts as the other packages (`dev`, `dev:now`, `build`, `lint`, `lint:ci`, `test` = `vitest --run --passWithNoTests`, `clean`, `format`) and the same dev tooling. The source is four files under `src/`: `main.ts` (the service: reads the config, checks the backup directory and lets `croner` run the job; started with `--now` it runs one additional backup and exits), `config.ts` (`getConfig()`: one typed `AppConfig`, in the style of Wichteln's `lib/config.ts`: required values throw, the rest has defaults; `RETENTION_DAYS` is required and only defaults to 31 when `NODE_ENV` is `development`, so the stack sets it in the compose file), `backup.ts` (`ensureBackupDir`, `runBackup`: `pg_dump`, retention) and `onedrive.ts` (the upload with the Graph client). `tsconfig.json` is the same as web's and Wichteln's where it can be (`ES2022`, `module: esnext`, `moduleResolution: bundler`, `isolatedModules`, `esModuleInterop`, `noEmit`, extensionless imports) and drops only what is Next.js-specific; there is no `"type": "module"`, as in the other packages. Because Node.js cannot resolve extensionless imports, `build` is `tsc` (type check) followed by esbuild, which bundles `main.ts` and its dependencies into one CommonJS file `dist/main.js`, the way Next bundles the other services; `dev` runs the sources with `tsx`. The image therefore needs neither `node_modules` nor a `package.json`. The token response is read with a small runtime field reader instead of a cast (the lint rules forbid unchecked casts).

**What the simplified backup no longer has.** `entrypoint.sh` and `backup.sh` (replaced by `main.ts` and `backup.ts`), the restore tool (`restore-backup`: argument handling, the refusal to restore into the production connection, the confirmation), and the OneDrive token helper (`get-onedrive-token`: device-code flow); the run-now command became the `--now` flag of `main.ts`. Restoring a dump becomes a documented manual step with `psql` and `pg_restore` inside the container (`DB_CONNECTION_STRING` of the container is the production database), and obtaining a refresh token becomes the documented manual device-code flow with `curl`; a rotated token is still logged by the upload. The restore requirement of the old `infrastructure` spec is therefore dropped instead of moved. Trade-off: the safety checks of the restore tool are gone, and a wrong connection string in a manual `pg_restore` is now the operator's risk; the manual commands in the README repeat the warning.

**The service schedules itself with `croner`.** Instead of `crond` plus `entrypoint.sh`, `main.ts` creates a `Cron` job from `BACKUP_SCHEDULE` (default `0 3 * * *`; `croner` is a dependency-free cron library that handles day-of-month and day-of-week like cron, the local time zone of the process (UTC in the container) and waits longer than the 24.8 days a single Node.js timer allows). It runs the job with `protect: true` (a run that is still going makes the next one skip) and a `catch` handler (a failed run is logged and the next scheduled time is awaited). The service fails at start-up, as an uncaught error, when the config is invalid (`DB_CONNECTION_STRING`, `MICROSOFT_GRAPH_APPLICATION_ID` or `ONEDRIVE_REFRESH_TOKEN` missing, a `RETENTION_DAYS` that is not a number of days), the backup directory is not writable or the schedule is invalid (the `Cron` constructor throws), and exits on `SIGTERM`/`SIGINT` (as the main process of a container it would otherwise ignore them). Output goes to stdout. `croner` is a regular dependency of the package, but esbuild bundles it into `dist/main.js`. Alternatives: a hand-written cron parser and timer loop (written first, replaced because a maintained library does the same with less code of our own); `node-cron` (smaller API, no `nextRun` and no overlap protection); `cron` (pulls in `luxon`). The compose health check is `pidof node`, because the process exits on any start-up failure and the schedule keeps it alive.

**The job keeps the old guarantees.** A failed `pg_dump` removes the partial dump; a failed upload keeps the local dump (it is then the only copy) and skips the retention cleanup, which only runs after a successful upload and deletes dumps older than `RETENTION_DAYS` whole days (like `find -mtime +N`). `pg_dump` gets the connection string as `--dbname`; the log shows only database and host. `pg_dump` runs through `spawn` because no library dumps a PostgreSQL database itself (the npm packages wrap the `pg_dump` binary or ship binaries of one fixed version, here 18 and 19, whose dumps a PostgreSQL 16 server cannot restore) and the image installs the matching client from Alpine anyway. The upload uses the Microsoft Graph client that the web application already uses (`@microsoft/microsoft-graph-client`): `OneDriveLargeFileUploadTask` with a `StreamUpload` creates the upload session, sends the file in chunks and finishes it, with `conflictBehavior: 'replace'`. The client does not refresh tokens, so `onedrive.ts` still requests the access token with the refresh token (one `fetch`) and logs a rotated refresh token. The behaviour of the client against Graph's upload API was checked with a local mock of the endpoints (session request, three 5 MiB chunks with `Content-Range`, replace), not against OneDrive.

**`dev` runs the service against the dev database.** The package's `dev` script (started by the root `pnpm dev` and `pnpm dev:backup`) runs `main.ts` in watch mode, so it idles until the next scheduled time. `dev:now` runs one backup right now (`main.ts --now`) outside docker with the same settings. Both load `services/.env`, which already holds the dev `DB_CONNECTION_STRING` that the service dumps (the same variable web and Wichteln use, passed to `pg_dump` as `--dbname`) and gets two more backup settings: `BACKUP_DIR=.backups`, i.e. `services/backup/.backups` (git-ignored), and a placeholder `ONEDRIVE_REFRESH_TOKEN` so that the upload fails and a dev run never uploads; they are documented in `infrastructure/env.example` as a commented block for `services/.env` only. `DB_CONNECTION_STRING` and `ONEDRIVE_REFRESH_TOKEN` are required, so a development run reaches production or uploads only if someone puts production values into `services/.env`. In the stack, `DB_CONNECTION_STRING` of the backup container is the production database (what the service dumps and the target of a prod restore); the manual restore into the dev database uses the fixed dev connection string written out in the README. The container needs no `BACKUP_DIR`: the default `/backup` is the folder the compose file mounts, and `BACKUP_DIR` is only set in the development `services/.env` (the infrastructure `.env` must not contain it, see `env.example`). Note: the dev machine's `pg_dump` is version 15, so a dump against the dev database (PostgreSQL 16) fails until that client is upgraded; the container image has the matching client.

**Backup Dockerfile like the application Dockerfiles.** `services/backup/Dockerfile` uses the same build stage as web and Wichteln (official pnpm image, `.nvmrc` Node.js, manifests-first install, `pnpm --filter @homeserver/backup build`, which bundles the entry points) with the repository root as build context. The runtime stage is `node:<exact tag>-alpine` plus `postgresql16-client` (with the comment about keeping the major in step with the `postgres` image) and copies `dist/` to `/app/services/backup` (the same layout and `WORKDIR` as web and Wichteln) and starts `node dist/main.js` as the default command. The container runs as the image's `node` user, which is possible now that `crond` is gone; the image creates `/backup` owned by `node`, and the bind-mounted host directory must be owned by uid 1000 (a one-time `chown` on the server, see the migration plan). The service checks at start-up that it can write to the backup directory, so a wrong owner fails loudly at deploy instead of at 03:00.

**Backup tests.** The package has the same vitest setup as the others (`*.tests.ts` next to the code) but no tests of its own now that the pure helper functions are gone: `test` is `vitest --run --passWithNoTests`, so the pull request's backup test job and the root `pnpm test` pass. The process runs (`pg_dump`, the HTTP calls to Microsoft) are verified manually.

**Published backup image, pulled by compose.** `ci.yml` builds `homeserver-backup` like the other images (context `.`, `file: services/backup/Dockerfile`), the deploy waits for all four, and compose uses `ghcr.io/<owner>/homeserver-backup:latest` without a `build:` section. The server no longer needs a build toolchain for the stack. Alternative: keep building on the host; rejected because it is the only image that does not follow the publish-then-pull flow and would not be covered by change detection.

**Pipelines and change detection.** `detect-changes.mjs` adds `backup` to `SERVICES`, so `services/backup/**` and the shared workspace files flag it. `pull-request.yml` gets a `backup` output, a `test-backup` job (`pnpm test` in the package), a stack-start build of the backup image when it changed, and `test-backup` in the quality gate's `needs`. `ci.yml`'s matrix gains an entry for the backup; every image is built with the repository root as context.

## Risks / Trade-offs

- [The two Dockerfiles drift apart again] → accepted: they are kept alike by convention and review, with no automated check; the runtime stage's Node.js version is pinned separately from `.nvmrc` and bumped by Renovate.
- [`pnpm runtime set node` or a native dependency fails on Alpine (musl)] → the pull request's stack start builds both images; the fallback is the Debian variants for both stages (`ghcr.io/pnpm/pnpm:<version>` and `node:<version>-slim`). If a native postinstall needs it, add `libc6-compat` back to the build stage.
- [`pnpm install --filter` with absent workspace folders resolves differently from the full install] → verified by the same builds; the old Dockerfiles relied on the same behaviour.
- [A new first-time image `homeserver-backup` must exist in GHCR before the deploy pulls it] → the same CI run publishes it before the deploy job, and the GHCR package must allow the deploy host to pull it like the other images.
- [Moving the folder renames paths in documentation, Renovate comment and compose] → covered by tasks; `grep -rn db-backup` must return nothing outside archived changes.
- [Linting reformats the existing backup scripts] → the first `pnpm lint` run reformats them; the diff is reviewed once with the rest.

## Migration Plan

Before the first deploy, on the server: `sudo chown -R 1000:1000 /opt/homeserver/backup`, so that the service, which now runs as user `node` instead of root, can write the dumps (the existing dumps stay readable and are deleted by retention like before). Without it the backup container exits at start-up with a message that the backup directory is not writable. Merge: the "CI" pipeline publishes the four images, rsyncs `infrastructure/` and recreates the stack; the backup container is then started from the pulled image. The old `./backup` data directory on the host and its volume mapping are unchanged. Rollback: revert the commit; the previous Dockerfiles and the compose file with the host build return together.
